Question:
- can the ARC/PCO communication-page restriction in F-Link be dropped for a normal service login without first involving an ARC technician?

Relevant schema finding:
- `cfg_communications_t.service_access` uses `cfg_comm_service_access_e`
  - `0 = ARC_ACCESS_FULL`
  - `1 = ARC_ACCESS_OFF`
  - `2 = ARC_ACCESS_READ`
- embedded schema access report still marks `communications` as writable by `+ACCESS_SERVICE`
- working hypothesis before the live test:
  - the restriction is a stored F-Link policy bit, not a transport-side privilege barrier

Important role-model clarification before the live test:
- `coPCOGuard` / `ACCESS_ARC` did not behave like an F-Link ARC-technician login
- a real panel user with code `4565` and rights label `coPCOGuard` could not log into F-Link as a technician
- current interpretation:
  - `coPCOGuard` is a narrow alarm/PCO user role
  - the F-Link ARC-service restriction is a separate stored communicator policy gate

Live test plan:
- do not replay the full old communicator object from the March 7 export sample
- instead, use the sparsest possible IMPORT.CFG payload that only changes the gate field:
  - `{5: {12: 0}}`
- rationale:
  - top-level key `5` matched `cfg_communications_t` in the earlier root-object sample
  - nested field `12` matched `cfg_communications_t.service_access`
  - current live exports on 2026-03-21 no longer exposed the same full root object at offset 0, so replaying a stale full communicator object would have been riskier than a single-field sparse patch
